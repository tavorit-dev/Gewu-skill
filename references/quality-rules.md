# 质量控制：四层验证

本 skill 的价值取决于能不能**稳定**产出准确的图，而不是偶尔画出几张漂亮的。
所以验证是核心能力，不是收尾步骤。

四层验证从抽象到具体，**顺序不能颠倒**——语义错了，视觉再完美也是错的图。

## 第一层：事实验证（最重要）

图形是否准确反映原文。

- [ ] 原文明确提到的关键组件是否都被正确表达？
- [ ] 执行顺序是否正确？
- [ ] 因果关系是否被错误地简化？（「A 之后发生 B」≠「A 导致 B」）
- [ ] 是否遗漏了影响结论的重要条件？
- [ ] **是否把「可能发生」表达成了「必然发生」？**
- [ ] 是否引入了原文没有支持的实现细节？

### 版本边界

涉及 Redis、Linux 内核、Go Runtime 这类版本差异大的技术时，
**必须保留版本边界**。不能把某个版本的实现直接泛化到所有版本。

`scope.version` 写清楚，`boundary` 里说明「本图描述 X 版本的实现」。

### 区分三类信息

| 类型 | 处置 |
|---|---|
| 原文明确陈述的 | 可直接进图，`evidence` 指向原文 |
| 有依据的解释推论 | 可进图，`evidence` 写清推理依据 |
| 原文没说明的 | **写进 `unknowns`，不要画** |

**宁可图上少一个节点，也不要把猜测画成事实。**

## 第二层：解释完整性

一张图至少应当回答一个明确的问题。

| 检查项 | 通过标准 |
|---|---|
| 问题明确 | 读者能知道这张图试图解释什么 |
| 机制完整 | 理解核心结论所需的关键步骤没有遗漏 |
| 关系清楚 | 参与者、箭头、状态之间的关系可以辨认 |
| 结论成立 | 图中表达能够支持标题或结论 |
| 限制清楚 | 关键假设或适用边界没有被隐藏 |

### 独立性测试

**如果读者必须先读完整篇文章才能看懂这张图的箭头和节点，这张图的独立性就不够。**

独立性不意味着图要包含所有细节——它应该独立解释**一个明确的问题**，
而不是取代整篇文章。

## 第三层：视觉质量

- [ ] 是否存在文字重叠？
- [ ] 是否有过多无意义的装饰？
- [ ] 是否出现不必要的交叉连线？
- [ ] 是否存在明显的视觉失衡？
- [ ] 核心机制是否足够突出？
- [ ] 在实际阅读尺寸下，文字是否清晰？

**硬约束：如果一个知识点无法在合理的图形尺寸内清晰表达，就拆图，不要不断缩小字体。**

渲染器在字号触及 11px 下限时**会报错并拒绝出图**，这是刻意的设计——
它在强制你拆图，而不是让你把问题藏起来。

## 第四层：自动修复（有限次数）

```
生成 VEM → 渲染 → 结构校验 → 实际渲染 → 像素校验 → 通过？→ 交付
                        ↑                              │否
                        └──────── 修复（最多 2 轮）─────┘
```

**最多两轮自动修复。** 问题仍在就输出待解决问题清单，而不是无限重试。

### 三类错误走不同的修复路径

| 错误类型 | 例子 | 修复路径 |
|---|---|---|
| **确定性错误** | XML 不合法、文字越界、元素缺失 | 程序自动修（校验器会指出具体位置） |
| **语义性错误** | 技术原理不准确、因果关系错误 | **回到 VEM 重新检查**，不能靠调布局解决 |
| **审美性问题** | 布局拥挤、视觉失衡 | 重新规划布局（通常是拆图） |

**语义错误不能用改坐标来"修复"。** 如果图里画错了机制，把它挪个位置还是错的。

## 交付前必跑的两道校验

```bash
# 1. 结构与几何（渲染前）：XML 合法性、越界、文字溢出、节点重叠
python3 scripts/render.py diagram.yaml -o diagram.svg --check
# 有 error 时退出码为 1，必须修完再交付

# 2. 渲染后像素（渲染后）：尺寸、墨色分布、留白、文字是否渲染出来
python3 scripts/render.py diagram.yaml -o diagram.svg --png diagram.png
python3 scripts/vis_check.py diagram.png --expect "ESTABLISHED" "TIME_WAIT"
```

## 能力边界：哪些验不了

**本环境 `Read` 打开图片只返回 `[Image #N]` 占位符，拿不到像素；`analyzeImage` 工具不存在。**

| 能验（程序化） | 验不了（必须人眼） |
|---|---|
| XML 合法性、元素白名单 | 文字是否糊 |
| 元素是否越出画布 | 是否有视觉重叠 |
| 文字是否超出节点框（测量复算） | 中文是否正确渲染（缺字会显示豆腐块） |
| 节点是否重叠 | 排版观感是否失衡 |
| 尺寸、墨色占比、留白分布 | **技术语义是否正确** |
| 英文标签是否真的渲染出来（OCR） | |
| GIF 是否真的在动（抽帧比对） | |

本机 `tesseract` 只装了 `eng` 语言包，**中文必然识别成乱码**——
所以 OCR 只能用来确认「文字渲染出来了」，不能用来判断中文是否正确。

### 交付时必须说清楚

**明确区分「已验（程序化）」和「未验（视觉/语义）」，把视觉终检交给用户。**

不要因为 `--check` 通过了就说「图没问题」——它只证明了图在几何上站得住，
没证明图讲对了机制。**没验的部分就说没验。**

## 质量指标

建立基线用，不必在没测试时就设定精确目标：

| 指标 | 评估方式 |
|---|---|
| 候选发现准确率 | 人工判断选出的知识点是否值得可视化 |
| 关键机制覆盖率 | 必要的机制是否出现在图中 |
| 技术事实错误率 | 影响理解的错误数量 |
| 图文一致性 | 图中关系是否符合原文及 VEM |
| 图形可读性 | 文字、布局、箭头、视觉层次 |
| 一次生成通过率 | 无需人工修正即通过校验的比例 |
| 修复成功率 | 自动修复后通过验证的比例 |

**最该优先关注三个：候选发现准确率、关键机制覆盖率、技术事实错误率。**
它们分别对应三种核心能力：选对内容、讲清机制、避免错误。
