# 技术原理提取与可视化 Skill：设计方案

我建议将这个 Skill 定位为一个 **面向技术知识的视觉解释引擎（Technical Visual Explainer）**。

它不是简单地把文章总结成思维导图，也不是把文字交给图像生成模型，让模型自由发挥，而是建立一套完整的处理流程：

**从文章中发现值得可视化的技术原理 → 提取关键机制 → 构建准确的解释模型 → 选择合适的视觉表达 → 生成可渲染的原理图 → 验证图文一致性。**

最终目标是：让读者通过一张图，在几十秒内理解一个技术概念的核心机制，同时保留足够的细节，让图能够用于技术博客、公众号文章、文档、课程和开发者知识库。

结合你之前对 SVG 原理动画、计算机知识解释图以及 Skill 工程化的关注，我建议优先采用 **SVG 原生渲染 + 结构化中间表示 + 多阶段验证** 的路线，而不是将图像生成作为主要实现方式。

这样既能控制技术细节的准确性，也能生成清晰、优雅、可缩放、易修改的图形。对于适合表现流程的内容，还可以进一步扩展为简单的 SVG 动画。

---

## 一、明确 Skill 的设计目标

### 1. 输入与输出

| 维度 | 设计 |
|---|---|
| 输入 | 一段技术描述、一篇文章、Markdown、技术文档、论文摘要或指定章节 |
| 核心任务 | 识别具有可视化价值的技术原理，并提取其关键机制 |
| 输出一 | 值得可视化的知识点及其筛选理由 |
| 输出二 | 每个知识点的准确性约束与解释模型 |
| 输出三 | 原理解释图，优先使用 SVG |
| 输出四 | 图形说明、关键结论、适用范围及必要的事实依据 |
| 可选输出 | 简单 SVG 动画、图组、原理图配套讲解文案 |
| 目标受众 | 开发者、技术学习者、工程师及技术内容读者 |

### 2. 核心设计原则

我建议确定以下六条原则。

**原则一：原理优先，而不是关键词优先。**

例如，文章中出现了 Redis、哈希表、渐进式 Rehash 等术语，不代表这些术语都值得单独画图。

真正值得可视化的内容可能是：

- 为什么 Redis 不一次性迁移整个哈希表？
- 扩容期间，新旧哈希表如何共同工作？
- 查询、插入和删除如何处理迁移中的数据？
- 渐进式 Rehash 如何在减少单次操作开销与增加实现复杂度之间进行权衡？

Skill 应优先发现能够通过视觉机制解释清楚的问题，而不是简单提取名词。

**原则二：图形必须解释机制。**

图不是装饰品。读者看完后，应当理解某件事情为什么发生、如何发生，或者不同方案为什么存在差异。

**原则三：准确性高于视觉效果。**

不能为了画面好看而虚构系统组件、执行顺序、数据关系或因果关系。

**原则四：一张图聚焦一个核心问题。**

复杂知识可以拆分成多张图。不要为了展示全面，把整篇文章压缩成一张拥挤的架构图。

**原则五：优先使用可控的图形渲染。**

结构、箭头、数据、文字和布局应当尽可能由程序确定，而不是依赖生成模型对文字和技术结构进行猜测。

**原则六：视觉表达应当客观、克制且优雅。**

不追求花哨、炫技或者过度拟物。视觉效果应该服务于理解。

# 二、整体架构：从文章到原理图的七阶段流水线

建议把整个 Skill 设计成一个多阶段处理系统，而不是一个简单的 Prompt。



整体工作流如下：

```text
┌───────────────────────────────────────────────┐
│                  输入层                       │
│                                               │
│  技术段落 / Markdown / 文章 / 论文 / 文档      │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 1：内容解析与上下文建立                │
│                                               │
│  提取主题、核心论点、技术术语、事实与限制      │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 2：可视化候选发现                      │
│                                               │
│  机制 / 流程 / 结构 / 对比 / 因果 / 权衡       │
│                                               │
│  为每个候选项计算可视化价值                    │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 3：原理提取与知识建模                  │
│                                               │
│  参与者、状态、动作、数据流、因果关系、约束    │
│                                               │
│  形成结构化原理模型                            │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 4：视觉表达方案选择                    │
│                                               │
│  流程图 / 时序图 / 状态图 / 结构图 / 对比图    │
│  数据迁移图 / 剖面图 / 因果图 / 机制示意图    │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 5：图形生成                            │
│                                               │
│  布局规划 → SVG 元素生成 → 图形组装            │
│  标注、箭头、图例、视觉层次、关键结论           │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 6：验证与质量控制                      │
│                                               │
│  技术正确性 / 图文一致性 / 布局 / 可读性        │
│  SVG 合法性 / 渲染结果 / 事实依据              │
└──────────────────────┬────────────────────────┘
                       ↓
┌───────────────────────────────────────────────┐
│  Stage 7：交付与迭代                          │
│                                               │
│  原理图 + 解释文案 + 依据 + 质量报告            │
│                                               │
│  根据验证结果修正并重新渲染                    │
└───────────────────────────────────────────────┘
```

这七个阶段有一个关键区别：

**前四个阶段解决“画什么、为什么画、应该怎么解释”；第五阶段才解决“如何画出来”。**

如果将这两类任务混在一起，模型很容易直接进入绘图状态，导致图形精美但知识提取不准确。

## 三、Stage 1：解析文章，建立知识上下文

### 3.1 不要直接对整篇文章生成图片

首先将输入内容解析成若干个语义单元。

每个语义单元可以包含：

```yaml
id: concept-001

title: Redis 渐进式 Rehash

source:
  section: "字典扩容机制"
  excerpt: "原文中与该机制有关的内容"

claims:
  - id: claim-001
    statement: "渐进式 Rehash 将迁移工作分散到多次操作中"
    type: mechanism
    confidence: high

entities:
  - name: ht[0]
    type: data_structure
  - name: ht[1]
    type: data_structure
  - name: rehashidx
    type: variable

relations:
  - from: ht[0]
    to: ht[1]
    type: migration

constraints:
  - "不能表现为一次性完成全部迁移"
  - "不能假设所有键都在同一时刻迁移"

open_questions:
  - "当前版本实现中，哪些操作会推进迁移？"
```

这里需要区分三类信息：

1. **原文明确陈述的事实**：可以直接用于图形表达。
2. **根据上下文得出的解释**：可以使用，但需要能够追溯推理依据。
3. **原文没有说明的信息**：不能擅自补成事实。

如果文章只介绍了基本原理，而没有给出具体实现细节，就不应该为了让图看起来完整而补造细节。

对于涉及版本差异的技术，例如 Redis、Linux 内核、Go Runtime，应当将版本作为可选的上下文约束。

当文章本身不足以支持某个关键结论时，Skill 可以提示需要补充资料，而不是直接猜测。

# 四、Stage 2：识别真正值得画图的内容

这是整个 Skill 最重要的能力。

我建议将候选知识点分成八类。

| 类型 | 适合解决的问题 | 推荐视觉形式 |
|---|---|---|
| 机制原理 | 某个功能究竟如何工作？ | 机制示意图、剖面图 |
| 执行流程 | 一个操作按照什么顺序执行？ | 流程图、时序图 |
| 数据结构 | 数据如何组织、关联和存储？ | 结构图、内存布局图 |
| 状态变化 | 系统在不同状态下如何变化？ | 状态机、状态迁移图 |
| 因果关系 | 为什么某个现象会发生？ | 因果图、机制链路图 |
| 方案对比 | 两种方案的差异及其代价是什么？ | 对比图、并列结构图 |
| 资源调度 | 任务、资源或请求如何分配？ | 调度图、泳道图 |
| 系统架构 | 多个组件如何协同工作？ | 架构图、组件交互图 |

此外，可以增加一个特殊类别：**反直觉知识**。

例如：

- 为什么增加缓存有时反而会增加延迟？
- 为什么异步操作不一定更快？
- 为什么多线程不一定能够提高吞吐量？
- 为什么渐进式迁移能够减少单次操作开销，却增加整体实现复杂度？

这类内容往往具有较高的解释价值，因为图形能够帮助读者发现直觉与实际机制之间的差异。

## 4.1 候选知识点评分

建议为每个候选知识点计算一个可视化优先级。

可以先采用以下启发式评分模型：

\[
S = 0.30M + 0.25V + 0.20E + 0.15I + 0.10R
\]

其中，各项均取 0～100 分：

| 维度 | 权重 | 评分依据 |
|---|---:|---|
| M：机制解释价值 | 30% | 图形能否帮助读者理解运作机制 |
| V：视觉表达优势 | 25% | 关系、变化或空间结构能否通过图形清晰表达 |
| E：教育价值 | 20% | 是否能够帮助读者建立正确的心智模型 |
| I：独立性 | 15% | 是否能够形成一张相对独立、完整的原理图 |
| R：可追溯性 | 10% | 是否有足够的原文依据支持图形内容 |

例如：

| 候选知识点 | 机制价值 | 视觉优势 | 教育价值 | 独立性 | 可追溯性 |
|---|---:|---:|---:|---:|---:|
| Redis 渐进式 Rehash | 95 | 95 | 90 | 90 | 95 |
| Redis 的基本定义 | 25 | 20 | 35 | 70 | 100 |
| 扩容期间新旧哈希表如何协作 | 95 | 100 | 95 | 90 | 90 |
| Redis 的发展历史 | 35 | 30 | 45 | 70 | 90 |

这里的分数仅用于展示模型如何工作，不代表对某篇具体文章的实际评估。

**建议将 70 分作为初始筛选参考线，而不是硬性规则。**

还需要增加三个约束：

- 文章没有提供足够依据时，不得仅因为可视化效果好就入选。
- 多个候选点如果解释的是同一个机制，应优先合并或建立图组。
- 对于非常简单、图形无法显著改善理解的内容，可以直接跳过。

最终输出的不是文章所有知识点，而是一份经过筛选的可视化候选清单。

# 五、Stage 3：把技术原理转换成结构化模型

在生成图形之前，需要将每个知识点转换为可验证的中间表示。

我建议为 Skill 设计一个核心数据结构：**Visual Explanation Model，简称 VEM**。

它相当于技术原理与 SVG 渲染器之间的桥梁。

## 5.1 VEM 的基本结构

```yaml
id: redis-rehash-001

title: Redis 如何渐进式迁移哈希表

question: 为什么扩容时不一次性迁移全部数据？

core_message: >
  将数据迁移工作分散到多次操作中，
  以降低一次性迁移造成的长时间阻塞风险。

visual_type: data_migration

scope:
  system: Redis
  version: "按文章或用户指定版本确定"

actors:
  - id: old_table
    label: 旧哈希表
    role: migration_source

  - id: new_table
    label: 新哈希表
    role: migration_target

  - id: rehash_cursor
    label: 迁移游标
    role: progress_indicator

states:
  - id: before
    label: 迁移前

  - id: migrating
    label: 迁移中

  - id: completed
    label: 迁移完成

transitions:
  - from: before
    to: migrating
    trigger: "开始 Rehash"

  - from: migrating
    to: migrating
    trigger: "推进一部分迁移工作"

  - from: migrating
    to: completed
    trigger: "满足迁移完成条件"

relationships:
  - source: old_table
    target: new_table
    type: migration

invariants:
  - "图中应表现迁移过程具有渐进性"
  - "不能暗示全部数据在一次普通操作中完成迁移"

evidence:
  - source_ref: claim-001
    supports: "迁移工作分散执行"

unknowns:
  - "具体迁移步数及触发细节需要根据实现版本确认"
```

这个例子只是说明 VEM 的表达形式，不是完整的 Redis 实现规范。

实际生成时，应该根据原文补齐必要的状态、操作和约束。

## 5.2 为什么不直接生成 SVG？

因为原理模型与图形布局属于两个不同的问题。

例如，Redis 渐进式 Rehash 可以采用两种完全不同的视觉表达：

**方案 A：数据迁移图**

重点表现：

- 旧哈希表和新哈希表；
- 部分键值从旧表迁移到新表；
- 迁移游标逐步推进；
- 迁移完成后的状态。

**方案 B：时间序列图**

重点表现：

- 迁移开始；
- 多次操作逐步推进；
- 每次操作承担部分迁移工作；
- 迁移结束。

两种图都可以解释同一个原理，但它们适合回答不同的问题。

VEM 应当保持技术语义不变，而允许不同的渲染方案使用不同的视觉结构。

这也是后续扩展主题、样式和动画能力的基础。

# 六、Stage 4：设计一套真正适合技术解释的视觉语言

我不建议一开始就设计几十种图形模板。

更合理的做法是建立一套小而精的视觉语法，并根据技术知识的特点组合使用。

## 6.1 推荐的七种核心图形模板



| 模板 | 核心表达 | 典型用途 |
|---|---|---|
| Mechanism | 组件、作用关系和内部机制 | 缓存、垃圾回收、负载均衡 |
| Flow | 操作的步骤和分支 | HTTP 请求处理、编译流程 |
| Sequence | 多个参与者之间的时间顺序与消息 | RPC、网络协议、并发交互 |
| State | 状态及其转换条件 | TCP 状态机、任务生命周期 |
| Structure | 组件、数据结构及其组织关系 | 哈希表、内存布局、系统架构 |
| Comparison | 两种方案的相同点、差异和代价 | 同步与异步、不同缓存策略 |
| Causality | 原因、中间机制和结果 | 性能瓶颈、死锁形成、缓存失效 |

这七类模板足以覆盖大量常见的计算机原理解释场景。

后续再根据真实使用情况增加：

- 资源调度图；
- 内存与数据迁移图；
- 空间剖面图；
- 网络拓扑图；
- 数学模型图；
- SVG 动画模板。

## 6.2 视觉风格：优雅、客观、有技术感

建议为整个 Skill 建立统一的设计系统。

### 配色

采用中性背景与语义化强调色，而不是让每张图都使用一套随意生成的配色。

| 视觉角色 | 建议 |
|---|---|
| 背景 | 白色或低对比度浅灰 |
| 主文字 | 深灰或近黑 |
| 次级文字 | 中性灰 |
| 常规组件 | 浅灰或低饱和度蓝色 |
| 主要执行路径 | 蓝色 |
| 关键状态或目标 | 青绿色 |
| 风险、阻塞、异常 | 克制使用橙色或红色 |
| 辅助关系 | 灰色虚线 |

颜色应当由图形语义决定，而不是每次随机分配。

例如，红色不应该仅仅表示“重要”，而应该在一张图中具有相对稳定的含义。

如果图中使用颜色表示数据状态，那么应当提供图例，避免读者自行猜测。

### 排版

建议建立统一的视觉层次：

1. **标题**：一句话说明图要解释什么。
2. **核心机制**：图形中最重要的部分。
3. **辅助解释**：必要的标签、步骤、条件。
4. **结论**：帮助读者快速理解机制的关键句。
5. **边界说明**：版本、假设或特殊条件。

不要在图中重复整段文章。

每个标签尽量简短，将详细解释留给图下的配套文案。

### 图形语言

优先使用：

- 简洁的几何形状；
- 明确的方向箭头；
- 有意义的空间分组；
- 适度的留白；
- 清晰的视觉层级；
- 一致的线条粗细；
- 统一的图标风格。

避免：

- 无意义的装饰性发光；
- 过多渐变和阴影；
- 过度拟物；
- 纯粹为了视觉效果添加的组件；
- 大量小字和密集连线；
- 与实际技术机制不符的隐喻。

**技术感不应该依赖复杂效果，而应该来自结构清晰、关系准确、布局严谨。**

# 七、Stage 5：图形生成方案——优先 SVG

建议将 SVG 作为第一版的主要输出格式。

原因是技术原理图通常由文本、箭头、节点、路径、边界框和少量图标组成，这些内容非常适合使用矢量图形描述。

SVG 还具有可缩放、可编辑、易于嵌入网页和 Markdown 等优势。

## 7.1 推荐采用三层生成架构

```text
              VEM 原理模型
                   │
                   ▼
        ┌────────────────────┐
        │ Layout Planner     │
        │                    │
        │ 选择模板、布局方向  │
        │ 确定节点和空间分组  │
        └─────────┬──────────┘
                  │
                  ▼
        ┌────────────────────┐
        │ SVG Renderer       │
        │                    │
        │ 生成节点、箭头      │
        │ 生成文本和图例      │
        │ 应用视觉设计系统    │
        └─────────┬──────────┘
                  │
                  ▼
        ┌────────────────────┐
        │ Render & Validate  │
        │                    │
        │ SVG 语法检查        │
        │ 实际渲染            │
        │ 布局与内容检查      │
        └─────────┬──────────┘
                  │
                  ▼
              最终原理图
```

### 第一层：Layout Planner

负责将 VEM 转换为布局方案。

例如：

```yaml
canvas:
  width: 1200
  height: 720

layout:
  type: horizontal
  direction: left_to_right
  zones: 3

elements:
  - id: old_table
    zone: 1
    shape: container

  - id: migration
    zone: 2
    shape: directed_process

  - id: new_table
    zone: 3
    shape: container

annotations:
  - id: key_insight
    position: bottom
    role: conclusion
```

这只是一个示意性布局配置。实际元素的坐标、尺寸和连线需要由布局算法或经过约束的布局生成过程确定。

### 第二层：SVG Renderer

将布局转换为真正的 SVG。

建议采用：

- 程序生成基础图形；
- 模板控制排版和视觉规范；
- 模型负责生成必要的文字标签与语义结构；
- 对复杂的局部布局允许模型提出候选方案；
- 由程序验证元素关系和基本几何约束。

不建议完全依赖模型一次性输出几百行 SVG。

因为模型直接生成 SVG 时，容易出现：

- 文本超出容器；
- 箭头没有连接到正确节点；
- 连线相互穿插；
- 组件尺寸不一致；
- 图例与实际颜色不对应；
- 为了布局方便而遗漏关键机制。

通过中间表示和渲染器，可以将这些问题拆分为独立的验证任务。

### 第三层：Render & Validate

生成 SVG 后，必须进行实际渲染，而不能仅仅检查代码是否能够解析。

建议至少检查：

1. SVG XML 是否合法。
2. 是否使用了允许的 SVG 元素。
3. 关键文字是否完整显示。
4. 图形是否超出画布。
5. 箭头是否存在明显的连接错误。
6. 关键组件是否与 VEM 一一对应。
7. 最终图像是否清晰、易读。

需要注意：程序可以检查元素是否存在、坐标是否越界，但无法仅凭 SVG 语法证明技术原理正确。

因此，技术语义验证和视觉渲染验证必须分开进行。

# 八、Stage 6：建立质量控制闭环

如果希望这个 Skill 能够长期使用，而不是只能生成几张漂亮的示例图，质量控制必须成为核心能力。

我建议将验证分为四层。

## 8.1 第一层：事实验证

检查图形是否准确反映原文。

具体包括：

- 原文明确提到的关键组件是否被正确表达？
- 执行顺序是否正确？
- 因果关系是否被错误地简化？
- 是否遗漏了影响结论的重要条件？
- 是否把可能发生的行为表达成必然发生？
- 是否引入原文没有支持的实现细节？

对于版本相关的技术，必须注意版本边界。

例如，不同版本的 Redis、Go Runtime 或 Linux 内核，其内部实现可能存在差异。不能将某个版本的实现直接泛化到所有版本。

## 8.2 第二层：解释完整性

一张图至少应当回答一个明确的问题。

可以检查：

| 检查项 | 通过标准 |
|---|---|
| 问题明确 | 读者能知道这张图试图解释什么 |
| 机制完整 | 理解核心结论所需的关键步骤没有遗漏 |
| 关系清楚 | 参与者、箭头和状态之间的关系可以辨认 |
| 结论成立 | 图中表达能够支持标题或结论 |
| 限制清楚 | 关键假设或适用边界没有被隐藏 |

## 8.3 第三层：视觉质量

重点检查：

- 是否存在文字重叠？
- 是否有过多无意义的装饰？
- 是否出现不必要的交叉连线？
- 是否存在明显的视觉失衡？
- 核心机制是否足够突出？
- 在实际阅读尺寸下，文字是否清晰？

建议增加一个重要约束：

**如果一个知识点无法在合理的图形尺寸内清晰表达，就应该拆图，而不是不断缩小字体。**

## 8.4 第四层：自动修复

建议采用有限次数的修复循环：

```text
生成原理模型
      ↓
生成 SVG
      ↓
语义检查 ──────┐
      ↓         │
实际渲染        │
      ↓         │
视觉检查        │
      ↓         │
  是否通过？     │
   │       │     │
  是       否 ───┘
   │       修复
   ↓
最终交付
```

建议最多进行两轮自动修复。

如果问题仍然存在，则输出待解决的问题，而不是无休止地调用模型。

需要区分：

- **确定性错误**：XML 不合法、文字越界、元素缺失，可以尝试自动修复。
- **语义性错误**：技术原理不准确、因果关系错误，需要重新检查 VEM 和事实依据。
- **审美性问题**：布局不够协调、图形过于拥挤，可以尝试重新规划布局。

不同错误应该进入不同的修复路径。

# 九、Stage 7：交付的不只是图片

我建议让 Skill 默认生成一个完整的知识解释单元，而不仅仅是 SVG 文件。

每个被选中的知识点，可以交付以下内容：


# 十一、SKILL.md 的核心设计

下面给出一份可以作为初始实现基础的 Skill 入口规范。

---
name: tech-visual-explainer
description: 从技术文章、文档、论文或文本中识别具有可视化价值的技术原理，提取可验证的解释模型，并生成准确、清晰、优雅的 SVG 原理解释图。适用于计算机原理、软件工程、系统架构、算法、数据结构、网络协议和技术机制解释。
---

# Tech Visual Explainer

## 1. 目标

将技术文本转化为准确、易懂、具有视觉表现力的原理解释图。

重点是解释机制，而不是装饰文章或简单总结知识点。

## 2. 工作流程

必须按照以下阶段执行：

1. 解析输入，识别文章主题、核心论点和技术上下文。
2. 发现候选知识点，评估可视化价值。
3. 筛选知识点，合并重复内容。
4. 为每个知识点提取事实、组件、状态、操作、因果关系及适用边界。
5. 创建结构化 Visual Explanation Model。
6. 选择适合该知识点的视觉表达形式。
7. 生成 SVG 原理图。
8. 检查技术语义、图文一致性、SVG 合法性和视觉质量。
9. 根据检查结果进行有限次数的修复。
10. 输出图片、原理说明、依据及验证报告。

不得跳过原理建模阶段，直接根据文章生成最终图片。

## 3. 候选知识点筛选

优先识别以下内容：

- 运行机制
- 执行流程
- 数据结构
- 状态变化
- 因果关系
- 技术方案对比
- 资源调度
- 系统组件协作
- 反直觉现象
- 关键设计权衡

优先选择能够通过图形明显改善理解的内容。

不要为了提高输出数量而提取没有独立解释价值的知识点。

多个候选点解释同一机制时，应优先合并或组织为相关图组。

## 4. 技术准确性

必须区分：

- 原文明确陈述的事实
- 有依据的解释与推论
- 尚未得到验证的信息

不得编造技术细节、执行顺序、组件关系、数据、测试结果或实现机制。

当原文缺少必要信息时，应明确指出缺失内容。

涉及特定软件版本时，应保留版本边界，不得随意推广。

## 5. 原理模型

每张图在生成前都应建立结构化模型，至少包含：

- 核心问题
- 一句话结论
- 参与者或组件
- 关键关系
- 主要操作或状态
- 必要约束
- 原文依据
- 尚未确定的信息
- 推荐视觉模板

根据内容特点决定是否需要状态机、时间序列、因果链、数据迁移过程或其他结构。

## 6. 视觉设计

默认使用简洁、克制、清晰的技术插画风格。

优先使用：

- 几何图形
- 清晰箭头
- 有意义的空间分组
- 适度留白
- 一致的字体和线条
- 语义明确的配色
- 简洁的标签和图例

禁止添加不支持技术解释的装饰性元素。

禁止通过虚构组件或夸大视觉效果来强化结论。

复杂机制应拆分为多张图，而不是不断缩小文字。

## 7. SVG 生成

优先采用模板与程序化 SVG 渲染。

确保：

- SVG 结构合法
- 元素关系与原理模型一致
- 文字和图形处于画布范围内
- 箭头和连线表达正确
- 关键标签完整
- 图例与图形语义一致

对 SVG 执行实际渲染，并检查最终图像。

不能仅凭代码生成成功就认定图形合格。

## 8. 质量验证

分别验证：

1. 技术事实是否准确。
2. 核心机制是否完整。
3. 图形是否清楚地表达关键关系。
4. 文字、箭头和组件是否正确。
5. 实际渲染是否存在明显布局问题。
6. 结论是否超出原文证据。
7. 适用边界是否得到保留。

确定性错误优先通过程序修复。

语义错误必须回到原理模型重新检查。

最多进行两轮自动修复；无法解决的问题必须明确报告。

## 9. 输出规范

默认输出：

1. 文章主题和核心结论。
2. 候选知识点及筛选理由。
3. 最终选中的可视化知识点。
4. 每个知识点的原理解释。
5. 每个知识点对应的 SVG 文件。
6. 必要的事实依据和适用边界。
7. 质量验证结果。

用户明确指定只生成某张图、只分析候选知识点或只输出 SVG 时，应遵循用户指定的输出范围。

## 10. 工作原则

始终遵循：

- 原理优先于装饰。
- 准确性优先于视觉效果。
- 图形必须服务于理解。
- 一个核心问题优先对应一张图。
- 所有关键技术关系都应能够追溯到依据。
- 复杂内容可以拆图，不得为了完整而牺牲可读性。

这份入口文件负责定义工作方式，详细的评分规则、模型结构、图形模板和质量检查标准则应放在 `references/` 中，避免入口文件过于臃肿。

# 十二、关键能力：让 Skill 学会选择，而不只是学会画图

我认为这个项目真正的价值，不是 SVG 渲染能力。

SVG 生成、箭头绘制、流程图布局等能力都可以逐步工程化。更有价值的是：

**面对一篇复杂的技术文章，Skill 能够判断哪些内容最值得画、应该如何解释，以及什么样的图形能够最大程度地降低理解成本。**

建议重点投入以下三种能力。

## 12.1 从原文中发现隐含问题

例如，输入一段关于 Redis 渐进式 Rehash 的文章。

一般的摘要工具可能输出：

> Redis 使用渐进式 Rehash，将数据从旧哈希表逐步迁移到新哈希表，以降低一次性迁移的开销。

这句话没有错误，但解释价值有限。

更好的 Skill 应当进一步识别：

- 一次性迁移为什么可能造成阻塞？
- 迁移期间，数据可能处于什么状态？
- 新旧哈希表如何协作？
- 迁移工作如何逐步推进？
- 这个机制牺牲了什么？

然后从中挑选最值得通过图形解释的问题。

这些问题才是原理图的内容来源。

## 12.2 将复杂机制拆成恰当的图组

假设一篇文章详细解释 Redis 渐进式 Rehash。

不建议直接生成一张涵盖所有内容的大图。

可以组织为以下图组：

| 图编号 | 核心问题 | 推荐形式 |
|---|---|---|
| 01 | 为什么需要渐进式 Rehash？ | 一次性迁移与渐进式迁移对比图 |
| 02 | 旧哈希表的数据如何迁移到新哈希表？ | 数据迁移机制图 |
| 03 | 迁移过程中，查询和写入如何处理？ | 操作路径图 |
| 04 | Rehash 如何逐步完成？ | 状态变化图 |
| 05 | 渐进式 Rehash 的收益和代价是什么？ | 权衡对比图 |

最终图组应当根据原文实际覆盖的内容决定，而不是每篇文章都固定输出五张图。

## 12.3 让每张图具有独立的解释价值

每张图都应该具备：

- 一个明确的问题；
- 一个核心结论；
- 一组必要的组件；
- 一条能够理解的机制路径；
- 一个清晰的阅读入口；
- 必要时附带的条件与限制。

如果读者必须先阅读整篇文章，才能理解图中的箭头和节点，那么这张图的独立解释能力还不够好。

不过，独立性不意味着图必须包含所有技术细节。它应该独立解释一个明确的问题，而不是取代整篇技术文章。

# 十三、是否应该支持 SVG 动画？

我的建议是：**支持，但不要把动画作为第一阶段的核心功能。**

静态图和动画适合表达不同类型的知识。

| 知识类型 | 静态图 | 动画 |
|---|---|---|
| 系统架构 | 很适合 | 通常没有必要 |
| 数据结构 | 很适合 | 适合展示结构变化 |
| 状态机 | 适合 | 适合展示状态迁移 |
| 并发机制 | 可以展示结构 | 适合展示事件顺序，但需避免误导 |
| 数据迁移 | 适合展示整体关系 | 适合展示逐步迁移 |
| 算法执行 | 适合展示算法结构 | 适合展示逐步执行过程 |
| 方案对比 | 很适合 | 通常没有必要 |

建议后续增加 `animation-planner` 模块。

其工作流程为：

```text
原理模型
   ↓
判断是否需要动画
   ↓
定义关键帧
   ↓
确定状态与时间顺序
   ↓
生成 SVG 动画
   ↓
检查动画是否忠实表达原理
```

这里有一个重要约束：

动画必须来自原理模型中的真实状态变化，不能为了让画面更生动而随意增加运动。

例如，展示一个算法时，应当明确哪些元素发生了变化、变化的条件是什么、每个步骤之间有什么关系。

如果动画并没有比静态图提供更多信息，就不应该增加动画。

# 十四、第一版 MVP：控制复杂度，尽快验证效果

我建议采用三个阶段逐步实现。

## Phase 1：验证核心价值

**目标：验证 Skill 是否真的能从文章中发现有价值的原理，并生成准确、易懂的图。**

第一版只需要：

- 支持粘贴文本和 Markdown；
- 识别候选知识点；
- 进行可视化价值排序；
- 生成 VEM；
- 支持四种核心模板；
- 输出 SVG；
- 完成基本的语义与渲染检查。

建议首批只实现以下模板：

1. 流程图；
2. 机制图；
3. 结构图；
4. 对比图。

选择四种模板的原因是，它们能够覆盖大量常见的计算机知识解释场景，而且实现成本相对可控。

第一版不必实现：

- 多 Agent 协作；
- 自动联网检索所有技术事实；
- 复杂的动画引擎；
- 自动生成无限数量的图；
- 多套视觉主题；
- 完整的图形编辑器。

这些能力可以在验证核心流程后逐步加入。

## Phase 2：提升解释质量

重点增加：

- 时序图与状态图；
- 多图之间的关联；
- 更严格的技术事实验证；
- 自动识别图形拥挤问题；
- 基于实际渲染结果的修复；
- 可复用的视觉设计系统；
- 更多计算机原理示例。

这一阶段的重点不是增加图形数量，而是提升图形的准确性和可读性。

## Phase 3：形成完整的技术知识视觉化工作流

在前两个阶段验证成功后，再考虑：

- SVG 动画；
- 文章章节级别的自动图组规划；
- 图文配套生成；
- 多种输出尺寸；
- 面向不同读者的解释深度；
- 历史图形的重新渲染；
- 可选的图片格式导出；
- 更复杂的图形模板。

此时，Skill 就不再只是一个图片生成工具，而是一套可复用的技术知识视觉化系统。

# 十五、如何评估这个 Skill 是否真正有效？

建议从第一版开始就建立测试集，而不是仅凭几张效果不错的图片判断质量。

可以选取以下五种具有代表性的技术文章。

| 测试场景 | 验证重点 | 预期结果 |
|---|---|---|
| Redis 渐进式 Rehash | 数据迁移与状态变化 | 能够准确表达新旧哈希表的协作关系 |
| Go 接口与 nil | 类型与运行时语义 | 不混淆接口值、动态类型和值 |
| Redis 缓存策略 | 数据流与方案对比 | 清楚表达缓存命中、失效和更新路径 |
| HTTP 请求处理 | 多组件执行顺序 | 组件关系与请求路径一致 |
| 并发任务调度 | 资源竞争与执行顺序 | 不将可能发生的执行顺序误画成必然顺序 |

对于每个测试场景，建议同时保存：

1. 原始文章；
2. 候选知识点清单；
3. 预期解释重点；
4. VEM；
5. 生成的 SVG；
6. 事实检查结果；
7. 视觉检查结果；
8. 人工评审意见。

这样可以在调整 Skill 指令、模型或渲染器之后，重新运行同一批测试，观察实际改进。

## 推荐的质量指标

可以从以下指标开始：

| 指标 | 评估方式 |
|---|---|
| 候选发现准确率 | 人工判断选出的知识点是否值得可视化 |
| 关键机制覆盖率 | 检查必要的机制是否出现在图中 |
| 技术事实错误率 | 统计影响理解的错误数量 |
| 图文一致性 | 检查图中关系是否符合原文及解释模型 |
| 图形可读性 | 检查文字、布局、箭头和视觉层次 |
| 一次生成通过率 | 统计无需人工修正即可通过检查的比例 |
| 修复成功率 | 统计自动修复后通过验证的比例 |

这些指标应该通过真实样本逐步建立基线，不必在尚未测试时就设定看似精确的目标值。

其中，我认为最值得优先关注的是三个指标：

**候选发现准确率、关键机制覆盖率、技术事实错误率。**

因为它们分别对应这个 Skill 最核心的三种能力：选对内容、讲清机制、避免错误。

# 十六、最终建议：把项目定位为技术解释引擎，而不是图片生成器

综合来看，我建议将这个 Skill 的能力划分为三个层次。

### 第一层：知识发现

回答：

- 文章中有哪些值得解释的原理？
- 哪些内容最适合图形化？
- 哪些知识点应该合并或拆分？
- 为什么值得画？

### 第二层：技术解释

回答：

- 机制究竟如何工作？
- 哪些组件参与其中？
- 它们之间是什么关系？
- 哪些条件不能忽略？
- 哪些结论有依据，哪些仍然不确定？

### 第三层：视觉表达

回答：

- 使用哪一种图形最合适？
- 如何组织组件和信息？
- 如何控制视觉层次？
- 如何生成并验证最终 SVG？
- 是否需要进一步转换为动画？

三层之间通过 VEM 连接，形成一套可以复用和迭代的工作流。

**我的最终推荐是：**

1. Skill 名称采用 `tech-visual-explainer`。
2. 以“可视化候选发现 + VEM + SVG 渲染 + 质量验证”为核心架构。
3. 第一版聚焦计算机技术原理，先支持流程图、机制图、结构图和对比图。
4. 将视觉设计规范与技术语义规范分离。
5. 不依赖模型一次性生成完整 SVG，而是通过结构化模型与程序化渲染控制结果。
6. 暂缓复杂动画和多 Agent 架构，先验证原理提取与图形解释质量。

**最重要的设计判断是：不要把 Skill 的成功标准定义为“生成了一张漂亮的图”，而应该定义为“从一篇文章中找到了真正值得解释的机制，并用一张准确、清晰的图让读者更容易理解它”。**

只要这一点做扎实，后续无论扩展到 SVG 动画、技术公众号配图、知识库可视化，还是自动化技术文章配图，都可以复用同一套核心能力。
